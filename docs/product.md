# 我们的明天：产品规格

> 记录每个昨天，共度每个今天，奔赴所有明天。

本文是 OurTomorrow（中文名“我们的明天”，简称“明天”）的产品范围基线。它描述产品承诺、信息架构、关键业务规则和阶段 0–6 的验收边界。接口、权限和实现细节分别以 `api.md`、`security.md` 与 `architecture.md` 为准。

## 1. 产品定义

“明天”是只属于两位伴侣的私密时间空间，不是公开社交网络、情侣评分工具、即时聊天软件或重型任务管理器。产品围绕三条相互连接的时间线展开：

| 时间 | 领域           | 用户价值                     | 代表内容                     |
| ---- | -------------- | ---------------------------- | ---------------------------- |
| 记录 | 已发生的过去   | 保存、补全并重新遇见共同经历 | 回忆、双方视角、照片、地点   |
| 日常 | 正在发生的现在 | 用低成本表达、感知与陪伴     | 状态、便利贴、交换日记、心情 |
| 明天 | 尚未发生的未来 | 写下期待、共同计划并兑现     | 愿望、纪念日、时间胶囊       |

产品的核心闭环是：

```text
把愿望写进明天
  → 在日常中一起实现
  → 完成后沉淀为记录
  → 在未来某天重新遇见过去
  → 产生新的期待
```

任何阶段性实现都不能破坏这个闭环，也不能把三个时间领域退化为彼此无关的功能列表。

## 2. 产品原则与非目标

### 2.1 必须遵守的原则

1. **共同创作**：共享内容允许双方参与；个人视角、日记答案等内容仍保留作者边界。
2. **记录足够轻**：一句话、一个心情、一张照片或一次轻触应能在几十秒内完成。
3. **有仪式感，无打卡压力**：不提供连续签到惩罚、亲密度排行、关系得分或双方贡献比较。
4. **私密优先**：没有公共主页、陌生人访问、内容推荐和广告；不默认接入第三方行为分析。
5. **时间是一等公民**：区分发生、创建、展示、解锁、重复和转换时间，并以情侣空间时区解释日历日期。
6. **服务端执行秘密与时间规则**：定时便利贴、交换日记揭晓和胶囊解锁不能只靠前端隐藏。
7. **温和恢复使用**：长期未记录时温和提醒继续，不显示断更天数或制造内疚。

### 2.2 明确不做

- 不提供公开成员体系、关注、点赞排行、陌生人搜索或内容广场。
- 不构建替代微信等工具的连续聊天能力；抱抱信号有频率限制。
- 不持续获取定位；地点由用户主动选择或填写。
- 不让 AI 代写关键情感内容。后续 AI 只做私密整理、检索或可撤销的建议。
- V1 不承诺视频、语音、端到端加密或复杂项目管理。
- 删除任一成员不会把共享空间自动转交给第三人；空间始终最多两名有效成员。

## 3. 用户与空间模型

产品不是传统多租户 SaaS，而是固定两个人共用的私密应用：

| 本地状态       | 能力                                              |
| -------------- | ------------------------------------------------- |
| 尚未选择角色   | 只能看到姓名匹配与隐私说明                        |
| 已选择男生身份 | 以 `boy`/slot 1 成员使用共同空间；默认称呼为“甲”  |
| 已选择女生身份 | 以 `girl`/slot 2 成员使用同一空间；默认称呼为“乙” |

身份相关本地数据只在 `localStorage` 的 `our-tomorrow-role-v2` 保存 `boy` 或 `girl`；theme、reduce-motion、touch-arrivals 等非敏感 UI 偏好也可以本地保存，正文、媒体和 Couple/API 实体不能持久化。姓名匹配不是认证，能访问部署入口的人仍可绕过前端并切换两种角色；部署必须由两人控制的设备、网络或外部访问代理保护。数据库中固定存在一个 Couple 和两名有效成员，后台维护、数据库访问或备份操作不构成产品内“第三位成员”。

## 4. 信息架构

### 4.1 路由图

| 路径        | 页面     | 访问条件   | 主要职责                                                 |
| ----------- | -------- | ---------- | -------------------------------------------------------- |
| `/login`    | 姓名验证 | 未选择角色 | 输入真名匹配固定角色，播放身份揭晓动画并说明私有部署边界 |
| `/today`    | 今日     | 已选择角色 | 聚合关系、对方此刻、纸条、日记、纪念日、随机回忆和愿望   |
| `/remember` | 记录     | 已选择角色 | 时间线、日历、相册、足迹、第一次                         |
| `/daily`    | 日常     | 已选择角色 | 此刻状态、交换日记、便利贴、心情和轻互动                 |
| `/tomorrow` | 明天     | 已选择角色 | 愿望、计划、纪念日、胶囊和未来地图                       |
| `/us`       | 我们     | 已选择角色 | 双方资料、关系信息、回顾统计                             |
| `/settings` | 设置     | 已选择角色 | 主题、时区、身份切换、隐私、导出、回收站和备份状态       |

`/identity` 重定向到 `/login`；停用的 `/join` 与 `/onboarding` 也重定向到 `/login`，不再呈现旧流程。未选角色访问私密路由回到 `/login`，已选角色再次访问 `/login` 则进入 `/today`。

移动端主导航固定为“记录 / 日常 / ＋ / 明天 / 我们”；`/today` 由品牌入口、首页按钮或启动路由进入。“＋”先询问时间维度，再展示具体内容类型：

```text
记录一件过去 → 回忆 / 第一次 / 补写日记 / 旧照片
留下此刻     → 便利贴 / 心情 / 状态 / 交换日记
写给明天     → 愿望 / 计划 / 时间胶囊 / 纪念日
```

桌面端使用左侧主导航；移动端和桌面端共享路由、领域语言和状态，不维护两套产品。

### 4.2 今日首页的聚合顺序

第一屏展示关系主卡、对方仍有效的最新状态，以及“记录 / 日常 / 明天”三个入口。第二屏按以下优先级最多展示少量卡片，不做无限信息流：

1. 对方刚留下且已到展示时间的便利贴；
2. 即将到来的纪念日；
3. 今日交换日记状态；
4. 一条满足去重规则的旧回忆；
5. 一个未完成的共同愿望；
6. 一个已完成但尚未转化的愿望。

## 5. 领域功能规格

### 5.1 记录：过去

一条回忆包含共享部分（标题、发生时间、地点、正文、封面、标签、是否第一次）和每位成员各自的视角。共享部分双方可维护且保留修改记录；每个人只编辑自己的视角。

时间线必须支持游标分页，并逐步提供按年份、月份、地点、标签、“第一次”和视角完整度筛选。删除默认进入回收站而不是立即物理删除。媒体属于情侣空间，不能通过猜测资源 ID 或永久公开地址读取。

完整体验包括：

- 双方视角都提交后显示完整状态；只有一方提交时不得泄露未写内容。
- 评论与表情回应服务于共同补全，不形成公开互动指标。
- 首页随机回忆执行安全筛选；阶段 6 的 Couple 每日盲盒持久记录展示日期并避免最近 8 次短期重复。
- 足迹与未来地图只展示用户主动添加的地点，不请求持续定位，也不加载第三方地图或瓦片。输入地点时可以由高德 Web 服务提供候选地址和经纬度，用户仍可手动填写。
- “第一次博物馆”优先由回忆的 `isFirstTime` 标记派生，而非复制正文。
- 每个 Couple 按情侣空间本地日期只有一个回忆盲盒；两种角色看到同一条记录，显式打开前不返回回忆内容，也可以主动忽略当天盲盒。

### 5.2 日常：现在

**此刻状态**带可选失效时间。过期状态不再出现在首页，但可按规则转为日常碎片。

**便利贴**支持类型、颜色、图标、置顶、计划显示、失效、阅后保留/消失和回应。计划显示前，接收方 API 不得返回正文。便利贴可显式转换为愿望、纪念日或回忆，转换操作记录来源关系，不能通过复制后失去追溯。

**交换日记**以情侣空间时区的自然日为一期。每位成员同日只能有一份答案，状态按以下规则推进：

```text
编辑中 → 已提交 → 等待对方 → 双方提交 → 已揭晓
```

双方都提交前，任何列表、通知、实时事件和错误详情都不得包含对方答案。揭晓后正文锁定，只允许追加附言。

**今日心情**是每人每天一个主心情与可选说明；公开范围和“希望回应”由作者决定。趋势只做共同关键词和时间变化，不做双方比较或情绪分数。

**抱抱信号**只允许七种固定 kind，不接受自定义消息。服务端按发送者执行 30 秒冷却和滚动一小时最多 12 次限制；在线时展示克制的到达浮层，离线站内通知只保存固定 kind，不包含自由文本。到达浮层可以在当前浏览器关闭，站内事实记录不受影响。

**冷静信箱**的延迟可用时间由服务端 Clock 和持久化任务推进。作者始终能读取自己写下的正文；收件人即使已到解锁时间，也必须显式执行 open 后才能获得正文。列表和未打开详情只提供元数据。

### 5.3 明天：未来

愿望状态为：

```text
有个想法 → 已计划 → 正在实现 → 已完成 → 已转化为回忆
```

状态只能向有效后继推进；需要纠错时使用显式撤销动作并记录审计，而不是直接改数据库。愿望完成后，系统提出“把这件未来写进记录吗”，转换时至少带入原愿望标题、创建时间、完成时间、地点、期待、照片和来源 ID。重复请求不得创建多条回忆。

纪念日支持自定义日期、情侣空间时区、每年重复、提前提醒、背景照片、往年回忆和今年计划。闰日等边界由后端统一算法处理。

时间胶囊状态为：

```text
草稿 → 已封存 → 锁定中 → 已解锁 → 已打开 → 已转化为回忆
```

封存后正文和附件不可修改；未到服务端解锁时间时 API 不返回正文。共同胶囊可要求双方确认开启，打开记录必须可审计。打开后可幂等转换为回忆。

### 5.4 跨时间转换

| 来源     | 目标                 | 前置条件               | 必须保留的溯源                              |
| -------- | -------------------- | ---------------------- | ------------------------------------------- |
| 便利贴   | 愿望 / 纪念日 / 回忆 | 作者发起；目标字段确认 | `sourceType=NOTE`、来源 ID、转换人和时间    |
| 愿望     | 回忆                 | 状态为已完成           | 创建/完成日期、愿望内容和关联媒体           |
| 时间胶囊 | 回忆                 | 已打开                 | 胶囊 ID、打开时间和允许公开到共享回忆的内容 |
| 交换日记 | 月度合集（规划）     | 当期已揭晓             | 日期、双方作者归属；不改变原文              |
| 纪念日   | 纪念回忆             | 纪念日已发生           | 纪念日 ID、年份和今年计划                   |
| 此刻状态 | 日常碎片             | 作者显式保存           | 原状态与有效期                              |

转换不是后台静默复制。用户必须看到预填内容并确认；目标保存成功后才更新来源状态。失败可安全重试。

### 5.5 阶段 6 已实现增强

- `Place` 同时保留历史状态 `UNVISITED / VISITED / LIVED` 和未来状态 `NONE / WANT_TO_GO / PLANNED / DEPARTING / COMPLETED`。完成关联愿望或计划会在同一事务中把地点写入共同足迹；若仍有其他未来安排，地点可以同时出现在历史与未来视图。
- 年度回忆书汇总当年 PUBLISHED 回忆、年度足迹、完成愿望、有效图片和标签关键词，不读取私人心情、日记、胶囊或冷静信正文。READY 状态可以重新生成统计并继续编辑双方寄语、年度照片和下一年信件；PUBLISHED 后冻结。年度照片只允许从对应年份 PUBLISHED 回忆的 READY 图片中选择。
- PWA 只提供安装、离线应用 shell 和静态资源缓存。应用进入后台时立即遮盖私密内容；返回前台后清空内存私密数据、按本地 `boy`/`girl` 选择重新读取当前身份，成功后才移除隐私幕。
- 完整导出新增地点双状态、固定 kind TouchEvent、按作者/显式打开规则裁剪的 CalmLetter、每日 MemoryResurface 和 AnnualReview；未打开盲盒不导出关联回忆 ID，未打开冷静信不导出收件正文。

当前阶段 6 不包含“今日一件小事”、未来来信、简单共同日历或月度合集；这些仍是后续候选，不应出现在已完成验收中。

## 6. 关键体验与验收场景

### 6.1 首次姓名匹配

1. 两人在受控设备或私有网络中打开应用。
2. 当前使用者输入真名；`示例用户甲` 匹配 `boy`，`示例用户乙` 匹配 `girl`，错误姓名提示“要输入真名喔”。
3. 服务端幂等建立固定两个用户、一个共同空间和 slot 1/2 成员关系。
4. Web 在匹配成功和揭晓动画后只保存 `boy` 或 `girl` 字符串，并在请求 header 中显式发送；非敏感 UI 偏好与身份数据分开。
5. 两个角色可分别完善自己的资料，共同设置关系签名、封面、开始日期和时区。
6. 任一设备可主动切换角色；切换时清空私密前端缓存并重新读取共同空间。

验收重点：错误姓名保持在登录页并显示“要输入真名喔”；正确姓名经过揭晓动画进入应用；重复、并发和服务重启后仍只有固定两名成员与一个空间；缺失/非法角色被拒绝；角色切换改变当前成员但不改变 Couple。姓名匹配本身不阻止冒用，外部访问边界必须单独验证。

### 6.2 共同完成一条回忆

1. A 创建共享回忆并上传图片。
2. A 提交自己的视角。
3. B 能读取共享部分并只编辑 B 的视角。
4. 双方视角完成后，两端显示完整状态。
5. 时间线能按发生时间重新找到这条回忆。

### 6.3 日记同时揭晓

1. A 提交答案后只能看到“等待对方”。
2. B 在提交前无法从接口、缓存、通知或实时载荷读取 A 的答案。
3. B 提交的同一事务使当期进入已揭晓。
4. 两端随后读取到双方答案；正文不可再改，附言可追加。

### 6.4 愿望成为回忆

1. 双方创建并推进一个愿望至完成。
2. 任一成员发起转换，确认预填内容。
3. 服务端在事务内创建一个带来源的回忆，并把愿望标记为已转换。
4. 重试同一转换只返回已有回忆。
5. 回忆出现在“记录”，愿望保留可追溯历史。

### 6.5 时间胶囊解锁

1. 作者封存胶囊后无法修改正文。
2. 到期前，即使修改浏览器时间、直接请求详情或订阅实时事件，也只获得元数据和锁定状态。
3. Worker 根据数据库中的持久化计划事件解锁；服务器重启不丢任务。
4. 到期后按单人/共同确认规则打开，并记录打开人和时间。

## 7. 发布范围

### 7.1 P0：首发闭环

- 固定 boy/girl 身份、本地角色选择、单一共同空间；
- 今日首页；
- 回忆 CRUD、图片、标签、双方视角、评论与回应；
- 状态、便利贴、定时显示、交换日记、心情；
- 愿望、计划、纪念日、时间胶囊；
- 愿望转回忆、便利贴转愿望；
- 站内通知和必要的实时更新；
- 时区、昵称、头像、主题；
- 软删除、回收站、完整导出；
- HTTPS、日志、备份、恢复演练和健康检查。

### 7.2 P1：浪漫增强

已完成：足迹地图、第一次博物馆、回忆盲盒、固定 kind 抱抱信号、冷静信箱、未来地图、年度回忆书和私密 PWA。

尚未交付：今日一件小事、未来来信、简单共同日历和月度合集。它们保留为后续候选，不能计入阶段 6 完成范围。

### 7.3 P2：长期探索

PDF 回忆册、自定义季节主题、默认静音的关系音乐、语音转文字、回忆整理建议、重复照片整理、私密摘要、WebAuthn，以及特殊信件的端到端加密。进入 P2 前必须分别完成隐私与数据迁移评审。

## 8. 阶段 0–6 交付计划

每个阶段在 `main` 上形成独立、可构建、可回滚的提交。阶段完成意味着代码、迁移、测试和文档同时达到门槛，不以页面“看起来完成”为准。

| 阶段                 | 目标                     | 主要交付                                                                                   | 阶段验收门槛                                                           |
| -------------------- | ------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 0 产品与视觉基础     | 建立共同语言和可运行骨架 | 品牌/设计令牌、路由壳、领域数据模型、API 约定、Nest/Vue 骨架、Compose、持久化 Worker、文档 | Web/API 可启动；迁移可执行；健康检查通过；移动与桌面壳使用统一视觉基础 |
| 1 两个人进入同一空间 | 建立固定且一致的双人空间 | boy/girl 身份选择、幂等初始化、显式角色 header、资料设置、共享 Couple、首页骨架            | 双角色始终映射同一空间；并发/重启不重复；版本与服务端时区测试通过      |
| 2 完成“记录”         | 双方共同保存过去         | 回忆时间线、图片、标签、地点、双方视角、评论回应、随机回忆                                 | 双方共同完成回忆并可按时间线找回；媒体和视角权限测试通过               |
| 3 完成“日常”         | 低成本留下当下           | 状态、便利贴、定时显示、交换日记、心情、站内通知                                           | 定时内容由服务端控制；日记同时揭晓且无侧信道泄露                       |
| 4 完成“明天”         | 兑现未来并闭环           | 愿望/计划、纪念日、胶囊、倒计时、愿望转回忆                                                | 愿望可幂等转为回忆；胶囊以服务端时间解锁；重启后任务继续               |

阶段依赖遵循 `0 → 1 → 2 → 3 → 4 → 5 → 6`。可以提前实现底层能力，但不能用阶段 6 的展示功能替代阶段 1–5 的安全和数据门槛。

## 9. 产品质量门槛

### 9.1 首发必须全部满足

- 过去、现在、未来均有可创建内容，愿望和胶囊能进入记录。
- 没有公开成员系统、公开资源或永久媒体 URL；部署入口由外部访问边界保护。
- 所有情侣空间资源在服务端按 `boy`/`girl` 固定映射得到的 `coupleId` 隔离。
- 未解锁胶囊和未揭晓日记的正文不出现在 API、通知或日志中。
- 回忆列表分页；图片懒加载；加载、空、错误和离线状态完整。
- 夜间模式可用；非必要动效尊重 `prefers-reduced-motion`。
- 重要破坏性操作有撤销期、回收站或二次确认。
- 完整导出不含部署/存储秘密、内部存储键和原始审计敏感信息。
- 数据库与媒体自动备份，并至少完成一次有证据的恢复测试。

### 9.2 非游戏化健康信号

产品健康只观察功能可靠性和闭环是否可用，例如创建成功率、定时任务延迟、导出成功率、恢复点新鲜度和愿望转换成功率。不得用“谁记录更多”、连续天数、互动排名或关系分数驱动使用。

若需要遥测，默认仅保留服务器运行指标，不采集正文、图片、心情、地点或胶囊内容；任何第三方分析必须先形成单独的隐私决策并由用户明确选择加入。

## 10. 文案基线

| 场景       | 推荐文案                               |

| 姓名验证页 | 这里没有访客，只有我们。               |

文案避免命令、评判、催促和性别假设。界面默认使用“对方”或成员昵称；示例中的“她/他”不能固化进业务模型。
